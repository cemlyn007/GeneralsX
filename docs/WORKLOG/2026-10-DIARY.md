### PLAN-023 Phase 5 Review Fixes (Round 3): Build, Write Access and Launcher Poisoning
- **Context**: Round 3 review of round 2's fix. `setPath_UserData` (`a6ac7d65d`) used `std::filesystem::create_directories`/`is_directory` unconditionally, but `GlobalData.cpp` only included `<filesystem>`/`<system_error>` inside `#ifndef _WIN32` (both games already keep the Windows default-directory branch filesystem-free) -- a Windows build of Zero Hour (win32-vcpkg or mingw-w64) failed to compile. The `create_directories`/`is_directory` pair also shared one `std::error_code`, so the stat's own result could mask the create's real failure. The check itself only asked `is_directory`, so an *existing* read-only directory -- the motivating read-only-`$HOME`-or-sandbox case when the directory is already there -- passed, and every later write still failed silently, the exact harm the round-2 fix was meant to close. Separately, rlgenerals' launcher called `setPath_UserData` even when it had chosen GlobalData's own unmodified default (no explicit or per-engine directory involved): after round 2's stricter validation, an uncreatable default with no override now raised `RuntimeError` from a call that runs after `Engine::boot` has set the priming/later-boot state, so it poisoned every later boot in the process with `FatalEngineError` -- worse than booting anyway, and contradicting PLAN-023's and the consumer plan's "still boots as before". Every `GlobalData` override (`newOverride()`'s `NEW GlobalData`, run for every `INI_LOAD_CREATE_OVERRIDES` block) also re-ran the default's derivation and creation, although `newOverride()` immediately overwrites the result with a copy, so an uncreatable default printed its stderr diagnostic once per override, not once per process.
- **Changes**:
  - `GlobalData.cpp` (Zero Hour): `<filesystem>`/`<system_error>` now included whenever `std::filesystem` is available (`!defined(_MSC_VER) || _MSC_VER >= 1914`, matching `UserPreferences.cpp`'s existing guard for the same gap), not only on non-Windows; `setPath_UserData` falls back to a small Win32-API directory-creation helper on VC6, which has no `std::filesystem`.
  - One static helper (`createUserDataDirectory`) replaces the create+stat+report sequence copied at both platform branches of the default directory and at `setPath_UserData`, using separate `std::error_code`s for the create and the stat so one cannot mask the other.
  - `setPath_UserData` now also probes for write access (create and remove a marker file) after confirming the directory exists, refusing an existing-but-read-only directory instead of accepting it.
  - The constructor (Zero Hour) and `parseGameDataDefinition` (Generals) now derive and create the default directory only for the original `GlobalData` instance, not for every override, since an override's value is about to be overwritten by `newOverride()`'s copy regardless.
  - rlgenerals' `launcher.cpp`: `choose_user_data_dir` reports whether it returned the plain, unmodified process default; `bring_up` skips the `setPath_UserData` call in exactly that case, so an unwritable default with no override given boots as it did before `setPath_UserData` existed, and only an explicit, prepared or per-engine directory is ever validated and can refuse the boot.
  - `PLAN-023`'s Phase 5 status updated for all of the above, and corrected on two points the round-2 text got wrong: the macOS default (unlike Linux's) has no `$XDG_DATA_HOME`-equivalent fallback, so with `$HOME` unset it is `./` itself, created nowhere.
