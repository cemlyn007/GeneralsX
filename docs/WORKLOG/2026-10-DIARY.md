## 02/10/2026
### PLAN-023 Phase 0: embedded-mode crash UI, fault latch, scratch-pad and save-listing fixes
- **Context**: follow-up changes to the 28/09 PLAN-023 Phase 0 prerequisites change, closing behavioural gaps and stale plan/audit text that change left. The behavioural fixes below landed without a worklog entry at the time; this entry covers them.
- **Changes**:
  - **Embedded-mode crash UI**: `ReleaseCrash`/`ReleaseCrashLocalized` no longer call `ShowWindow(SW_HIDE)`, `TriggerMiniDump()` (which shuts down the process-wide `MiniDumper`) or print the Linux "FATAL ERROR" stderr banner when `IsEngineEmbeddedMode()` is set, since a host embedding more than one engine keeps the window and the other engines running after the throw. The two throw sites per function are deduplicated through one `ThrowIfEmbedded` helper.
  - **Sticky fault latch**: new exported `HasEngineFaulted()`/`ClearEngineFault()` (`Common/FatalEngineError.h`), set by `ThrowIfEmbedded` right before every embedded-mode throw. A `catch (...)` between `RELEASE_CRASH` and a host entry point that swallows the exception instead of rethrowing it still leaves this latch set, so a polling host can detect the fault anyway. Clearing it is the host's job, at every point it handles a fault (caught or polled); rlgenerals' `launcher::mark_faulted` now does this unconditionally, since a host that only cleared it on the polling path left it set across the next, unrelated call after a *caught* fault.
  - **Per-instance scratch-pad maps** (`GameStateMap.cpp`/`.h`, both games): `clearScratchPadMaps` deletes only the paths this instance's own `extractAndSaveMap` wrote (`m_scratchPadMaps`), not every `*.map` in the shared, process-wide Save directory — the old whole-directory sweep could delete a scratch-pad map a different live engine still needed. The path is now recorded *before* `extractAndSaveMap` runs (deduplicated), so a partial file from a truncated or corrupt load is tracked and cleaned up too, not only a successful extraction. This does not make two engines safe to load or save the *same map leaf* concurrently: the scratch path is named after the map leaf alone, so they still collide on the identical file (documented on `m_scratchPadMaps`, PLAN-023's Phase 0 status table).
  - **`iterateSaveFiles`** (`GameState.cpp`, both games): on non-Windows, lists the save directory directly with `std::filesystem::directory_iterator` (case-sensitive, regular files only) instead of `TheLocalFileSystem->getFileListInDirectory`, which case-folded two differently-cased save files together and could hand a FIFO, socket or dangling symlink to the load path. A non-ENOENT directory error (permissions, a mid-read I/O failure) is now reported on stderr the same way `StdLocalFileSystem` does, so a silently short listing is not silent.
  - **Null-mode `NEW`/`MSGNEW`/`newInstance`/`newInstanceDesc`**: pass constant tag arguments to the exported `(size_t, const char *, int)` overload instead of `__FILE__, __LINE__`, which grew `libgeneralsx.so`'s `.rodata` with an absolute compile-time path per call site and leaked the sandbox's build path into otherwise-identical builds. The overload already discarded both arguments in Null mode.
  - **MiniAudio Bink PCM**: `MiniAudioStream::bufferData` no longer appends decoded Bink video PCM to `m_buffer` when the stream has no engine (`MiniAudioManagerDummy::getHandleForBink`'s streams never call `setEngine`), which grew unboundedly on a long video with nothing ever draining it.
  - **`SAGE_USE_FFMPEG` + OpenAL dummy**: a `#error` now fails the build if `SAGE_USE_FFMPEG` is on with the OpenAL dummy backend, since `OpenALAudioManagerDummy::getFileLengthMS`'s hardcoded 0 only matches the real backend while that option is off.
  - **`scripts/qa/test-gamememorynull-exports-linux.sh`**: fixed a SIGPIPE/pipefail bug (`printf ... | grep -qx`, which closes its producer's stdin as soon as it matches, killing `printf` with SIGPIPE under `set -o pipefail`) that made every "must be exported" check fail on any real binary regardless of whether the engine was correct. Wired into `bazel test` (rlgenerals' `//rlgenerals/generalsx:gamememorynull_exports_test`).
  - **Comment and plan-doc accuracy**: fixed a wrong pooled-build analogy and a stale macro-expansion claim in the zero-fill audit (`GameMemoryNull.h`, `ZERO_FILL_MEMBER_INIT_AUDIT_2026-09-27.md`); synced PLAN-023's consumer Answer 1 (thread migration) with the wording already revised in the base plan PR; corrected PLAN-023's claim that the MiniAudio dummy was never built (the `linux64-miniaudio` CMake preset compiled it, in Docker, on Linux; it had not yet been *run* -- see 03/10/2026 below for that); fixed PLAN-023's stale credit and status for the scratch-pad/`iterateSaveFiles` row, and its header's "Phase 0 done" against the same document's own pending acceptance criterion; recorded the Windows `extern "C"`/`/EHsc` exception-propagation gap in PLAN-023, where PR #18's description already claimed it was documented.
  - Backported to Generals where the files are duplicated.
- **Added**: a Bazel regression test on the rlgenerals side (`engine_saves_test`) that spawns a child engine process, loads a save (tracking one scratch-pad map), and asserts that an unrelated file placed in the shared Save directory survives that child's teardown — the pre-fix whole-directory sweep would have deleted it too.

## 03/10/2026
### PLAN-023 Phase 0: a tested init() rethrow site, a real MiniAudio run, and save-path hardening
- **`GameEngine::init`'s rethrow site** (both games): a `GENERALSX_TEST_FAULT_IN_INIT` environment hook, gated on `IsEngineEmbeddedMode()` (a no-op outside embedded mode, so retail and stock builds are unaffected), raises a fault at the top of `init()`'s own try block so a host's test can exercise that function's `catch (const FatalEngineError&) { throw; }` rethrow site specifically, not only a throw site reached before any engine code's own try block is entered. rlgenerals' `test_fault_inside_game_engine_init_raises_engine_fault` (`fault_test.py`) now asserts the raised `EngineFault`'s message is the hook's own text, not just its type: checking the type alone cannot tell this rethrow site apart from the generic `catch (...)` below it, which reaches an `EngineFault` of the same type through its own `RELEASE_CRASH` if the rethrow site were ever removed. The other roughly twenty engine-side rethrow sites between `RELEASE_CRASH` and a host entry point remain untested.
- **MiniAudio backend actually run, not just compiled**: the `linux64-miniaudio` CMake preset's `GeneralsMD/GeneralsXZH` binary was linked and run on Linux (Zero Hour assets, Xorg + `llvmpipe`/the host GPU for the Vulkan swapchain). With `-noaudio`, `SDL3GameEngine::createAudioManager` constructs `MiniAudioManagerDummy`; the process booted to the main menu and shut down cleanly. Without it, the same binary constructs the real `MiniAudioManager`, opens an actual playback device through its staged `openDevice`, boots to the main menu and shuts down cleanly. Both runs reach `~MiniAudioManager`, which calls `closeDevice()` directly; since that call runs while the object's dynamic type is `MiniAudioManager` (the derived dummy part has already been destroyed), it is the base class's own staged teardown that runs even for the dummy object, not the dummy's no-op override. PLAN-023's Phase 0 acceptance table is updated accordingly.
- **Save-path hardening** (`GameState.cpp`/`GameStateMap.cpp`, both games): non-Windows `iterateSaveFiles`' directory loop advanced with `dirIter.increment(ec)` as a `for` loop's own step, then checked `ec` in the body; both libstdc++ and libc++ reset the iterator to `end` on an `increment` failure, so the loop's own condition went false before that check ever ran, and a mid-read directory error stayed silent. Restructured as a `while` loop that checks `ec` right after each `increment`, before testing against `end`. `extractAndSaveMap` (`GameStateMap.cpp`) now closes its output file (and frees its read buffer) on every throw path, not only the ones it threw itself: `Xfer::beginBlock`/`xferUser` can themselves throw on a truncated or corrupt save, and used to leave the file handle open, which failed a later `DeleteFile` of that now-tracked partial file on Windows and leaked one descriptor per failed load elsewhere. Documented, next to `m_scratchPadMaps`, the gap that per-instance tracking does not close: a scratch map left by a process killed before its destructor ran, or by an embedded engine that faulted and was deliberately never destroyed, is cleaned up by nobody.
- **`ReleaseCrashLocalized` minidump ordering** (`Core/.../Debug.cpp`): the embedded-mode skip introduced on 02/10 moved `TriggerMiniDump()` to after the two `TheGameText->fetch()` calls and the `AsciiString::translate()` that builds the crash reason, even with the embedded-mode flag off. Moved it back to before the fetches (matching `ReleaseCrash` and the pre-02/10 behaviour): those calls can themselves fault on the corrupt state a crash dump exists to capture, and the minidump should reflect that state, not whatever two more lookups and a translation left behind. Only the `MessageBox`/`ShowWindow`/stderr block, which needs the fetched text, still runs after the fetches.
