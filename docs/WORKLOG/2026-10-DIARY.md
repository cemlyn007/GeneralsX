### PLAN-023 Phase 8, Stage RR4: Truly Concurrent Renderers
- **Context**: after RR3 every render engine owned its draw state, and rlgenerals' host ran N renderers behind a render mutex, one draw at a time. RR4 drops the mutex (rlgenerals) so that N engines update and draw at the same time on N threads, and fixes what ThreadSanitizer finds on the engine side.
- **Changes**:
  - `W3DDisplay::reset` (both games): the scene iterator steps past each render object before removing it. The removal frees the list node the iterator stood on to `MultiListNodeClass`'s process-wide pool, and `Next()` read its link from freed memory, which another engine's thread could take from the pool and overwrite in between (TSan: a node constructor on one renderer's draw against `Next()` in another's shutdown).
  - `WWMemoryLogClass`'s allocation and free counts, which `WW3D::Begin_Render` reads and resets every frame, are `thread_local`. Nothing calls `Allocate_Memory` or `Release_Memory` in this build, so they are always zero; the race was `Reset_Counters` writing that zero into the one process-wide pair from every drawing engine at once (TSan).
  - RR3 review follow-ups: `SnowManager::updateIniSettings`' generator is `snowRandom` (it shadowed POSIX `::random()`); `W3DShaderManager::setShader`, `resetShader` and the filter calls bind the fields they use once per call rather than looking the engine's `W3DShaderManagerData` up at every use. `PER_ENGINE_STATIC` slot indexes come from an atomic counter (`allocateEngineSlotIndex`), and a function-local one is a C++ magic static, so concurrent first use from N threads is race-free (no TSan report).
  - The render-const (84) and render-process (99) rows reviewed for concurrent use: constant tables, presets and key names built at static initialisation or under `std::call_once` and only read; the rest UI-only (no headless engine runs it) or the host's once-per-process state. None is a `RefCountClass` shared across engines; no atomic `NumRefs` was needed.
  - `PLAN-023_STATE_CLASSIFICATION.tsv` regenerated: the two counts are TLS, three definitions moved by a line.
- **Validation**: rlgenerals' `multi_engine_threads_render_test` (four renderers on four threads at four sizes; same seed, different maps, staggered, recreate, hand-off, busy, drain, fault) reports no ThreadSanitizer race on lavapipe at 400 frames a renderer, ASan on lavapipe and NVIDIA no memory error, and every renderer equals its solo run (CRCs, images, minimaps) on NVIDIA and lavapipe; four renderers draw at once in every variant that starts together. `VK_LAYER_KHRONOS_validation` with 2 and 4 renderers drawing at once reports only DXVK's two known shadow-sampler messages on both drivers. Render digests (NVIDIA `ad34d891`, lavapipe `d4721e35`), render lifecycle digests (`c8feb4f5`, `fd3c9668`) and the solo CRC md5 `ebf7cb56` unchanged with the context off and on; the one-renderer render benchmark (320x240, NVIDIA) within 0.1% of RR3's, and four render Envs on threads now step 4,304 times a second together (968 under RR3's mutex). Under ASan, NVIDIA render processes (solo ones included) leave four DXVK-internal allocations LeakSanitizer reports (resolved in the review fixes below).
- **Review fixes**: the viewer's SDL event pump is serialised with other engines' boots and shutdowns again. Without the host's render mutex, `SDL3GameEngine::pollSDL3Events` (every `update()` of the engine with a window) and `reset()`'s text-input stop ran with no lock beside another thread's offscreen boot or shutdown SDL calls (`W3DDisplay::init`'s `SDL_SetWindowPosition`, DXVK's `SDL_GetWindowSize(nullptr)`). `Common/ApplicationWindow.h` gains the embedding host's event pump lock (`ApplicationWindow_TryLockEventPump`, `ApplicationWindow_UnlockEventPump`, null for the game's own `main()`), which both games' pump and `reset()` take around their SDL calls; when the host's lock is busy the pump is skipped (its events stay queued) and `reset()` leaves the text-input stop to the next pump. rlgenerals sets them to try its process mutex. Both symbols are `render-process` in the classification and on the render probe's allowlist. The NVIDIA leaks: LeakSanitizer matches module names too, so rlgenerals' NVIDIA ASan run (`--config=asan_nvidia`) suppresses them with a module-wide `leak:libdxvk_d3d9.so` entry in its own suppression file. The leak is DXVK's memory allocator bookkeeping, made on its CS thread for a memory type NVIDIA exposes and lavapipe does not. The lavapipe runs keep the narrow entries, so an engine leak of a Direct3D resource is still reported there. With it, the concurrent render set under ASan on NVIDIA reports no memory error and no leak, and every renderer equals its solo run. Under ASan, DXVK creates its NVIDIA devices without CUDA interop, so each device adds 8 threads rather than 9 (no `cuda-EvtHandlr`).
- **Review fixes (round 2)**: `Common/ApplicationWindow.h` no longer says that the pump and `reset()` are the only SDL calls an engine with a window makes. `SDL3Mouse` makes SDL calls every frame (`draw()`'s `setCursor` calls `SDL_SetCursor`; the event translation calls `SDL_GetWindowFromID`, `SDL_GetWindowSize` and `SDL_GetMouseState`; `capture()` calls `SDL_CaptureMouse` and `SDL_SetWindowMouseGrab`), and so does `SDL3Keyboard`. Neither exists in a headless engine, though: `GameClient::init` makes no keyboard and a `MouseDummy` (no-op `setCursor`, `capture` and `releaseCapture`) when `GlobalData::m_headless` is set, and rlgenerals requires it of every render boot, its viewer's included. `W3DDisplay`'s window-mode calls run only in `init` (the boot, under the host's lock). The header now says this, and that a host with a non-headless window engine would have to lock those calls too.
- **Review fixes (round 3)**: the pump and `reset()` were still not the window engine's only SDL calls between its boot and shutdown. `W3DDisplay::draw` (both games) calls `DX8Wrapper::Pillarbox_Process_Resize` first thing every frame, whose window-size query (`SDL3_GetWindowSizeInPixels`: `SDL_GetWindowSize`, `SDL_GetWindowSizeInPixels`) and, on a resize, `Reset_Device` (which rebuilds DXVK's SDL surface) are SDL calls, made with no lock beside offscreen boots and shutdowns on other threads. With a window, `draw` now makes that call under the host's lock and skips it for the frame while the lock is busy; an engine without a window makes no SDL call there (both size providers return false without a window) and takes no lock, so concurrent offscreen renderers never contend for it. `EventPumpLock` moves into `Common/ApplicationWindow.h` (inline, replacing the copies in both `SDL3GameEngine.cpp`), and the hooks are `std::atomic` function pointers: the host stores Unlock, then TryLock with release; the lock loads TryLock once with acquire, then Unlock. The header now lists every SDL call of a headless window engine and why the rest (`SDL3Mouse`, `SDL3Keyboard`, `SDL3_ApplyWindowModeForRenderConfig`, reached only from `init` and the options menus) never run, and `~SDL3GameEngine`'s `SDL_StopTextInput` says it relies on the engine being destroyed by its shutdown, which such a host runs under the same lock. `wwmemlog.cpp`'s rationale is corrected: nothing calls `Allocate_Memory` or `Release_Memory`, so the counts are always zero, and the race was only `Reset_Counters`' writes. The NVIDIA LeakSanitizer finding predates RR4: an ASan build of the RR3 heads (rlgenerals 76c20c1, this repository f91ea6d03), one solo render process on NVIDIA (`multi_engine_threads_test --solo-render desert7 300`, lavapipe's suppressions only) reports the same four allocations (144 bytes direct; 196,608, 65,536 and 20 indirect; 262,308 in all) from `libdxvk_d3d9.so.0`.
