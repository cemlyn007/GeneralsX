## 02/10/2026
### PLAN-023 Phase 0: embedded-mode crash UI, fault latch, scratch-pad and save-listing fixes
- **Context**: follow-up changes to the 28/09 PLAN-023 Phase 0 prerequisites change, closing behavioural gaps and stale plan/audit text that change left. The behavioural fixes below landed without a worklog entry at the time; this entry covers them.
- **Changes**:
  - **Embedded-mode crash UI**: `ReleaseCrash`/`ReleaseCrashLocalized` no longer call `ShowWindow(SW_HIDE)`, `TriggerMiniDump()` (which shuts down the process-wide `MiniDumper`) or print the Linux "FATAL ERROR" stderr banner when `IsEngineEmbeddedMode()` is set, since a host embedding more than one engine keeps the window and the other engines running after the throw. The two throw sites per function are deduplicated through one `ThrowIfEmbedded` helper.
  - **Sticky fault latch**: new exported `HasEngineFaulted()`/`ClearEngineFault()` (`Common/FatalEngineError.h`), set by `ThrowIfEmbedded` right before every embedded-mode throw. A `catch (...)` between `RELEASE_CRASH` and a host entry point that swallows the exception instead of rethrowing it still leaves this latch set, so a polling host can detect the fault anyway. Clearing it is the host's job, at every point it handles a fault (caught or polled); rlgenerals' `launcher::mark_faulted` now does this unconditionally, since a host that only cleared it on the polling path left it set across the next, unrelated call after a *caught* fault.
  - **Per-instance scratch-pad maps** (`GameStateMap.cpp`/`.h`, both games): `clearScratchPadMaps` deletes only the paths this instance's own `extractAndSaveMap` wrote (`m_scratchPadMaps`), not every `*.map` in the shared, process-wide Save directory — the old whole-directory sweep could delete a scratch-pad map a different live engine still needed. The path is now recorded *before* `extractAndSaveMap` runs (deduplicated), so a partial file from a truncated or corrupt load is tracked and cleaned up too, not only a successful extraction. This does not make two engines safe to load or save the *same map leaf* concurrently: the scratch path is named after the map leaf alone, so they still collide on the identical file (documented on `m_scratchPadMaps`, PLAN-023's Phase 0 status table).
  - **`iterateSaveFiles`** (`GameState.cpp`, both games): on non-Windows, lists the save directory directly with `std::filesystem::directory_iterator` (case-sensitive, regular files only) instead of `TheLocalFileSystem->getFileListInDirectory`, which case-folded two differently-cased save files together and could hand a FIFO, socket or dangling symlink to the load path. A non-ENOENT directory error (permissions, a mid-read I/O failure) is now reported on stderr the same way `StdLocalFileSystem` does, so a silently short listing is not silent.
  - **Null-mode `NEW`/`MSGNEW`/`newInstance`/`newInstanceDesc`**: pass constant tag arguments to the exported `(size_t, const char *, int)` overload instead of `__FILE__, __LINE__`, which grew `libgeneralsx.so`'s `.rodata` with an absolute compile-time path per call site and leaked the sandbox's build path into otherwise-identical builds. The overload already discarded both arguments in Null mode.
  - **MiniAudio Bink PCM**: `MiniAudioStream::bufferData` no longer appends decoded Bink video PCM to `m_buffer` when the stream has no engine (`MiniAudioManagerDummy::getHandleForBink`'s streams never call `setEngine`), which grew unboundedly on a long video with nothing ever draining it.
  - **`SAGE_USE_FFMPEG` + OpenAL dummy**: a `#error` now fails the build if `SAGE_USE_FFMPEG` is on with the OpenAL dummy backend, since `OpenALAudioManagerDummy::getFileLengthMS`'s hardcoded 0 only matches the real backend while that option is off.
  - **`scripts/qa/test-gamememorynull-exports-linux.sh`**: fixed a SIGPIPE/pipefail bug (`printf ... | grep -qx`, which closes its producer's stdin as soon as it matches, killing `printf` with SIGPIPE under `set -o pipefail`) that made every "must be exported" check fail on any real binary regardless of whether the engine was correct. Wired into `bazel test` (rlgenerals' `//rlgenerals/generalsx:gamememorynull_exports_test`).
  - **Comment and plan-doc accuracy**: fixed a wrong pooled-build analogy and a stale macro-expansion claim in the zero-fill audit (`GameMemoryNull.h`, `ZERO_FILL_MEMBER_INIT_AUDIT_2026-09-27.md`); synced PLAN-023's consumer Answer 1 (thread migration) with the wording already revised in the base plan PR; corrected PLAN-023's claim that the MiniAudio dummy was never built (the `linux64-miniaudio` CMake preset compiled it, in Docker, on Linux; it had not yet been *run* -- see 03/10/2026 below for that); fixed PLAN-023's stale credit and status for the scratch-pad/`iterateSaveFiles` row, and its header's "Phase 0 done" against the same document's own pending acceptance criterion; recorded the Windows `extern "C"`/`/EHsc` exception-propagation gap in PLAN-023, where PR #18's description already claimed it was documented.
  - Backported to Generals where the files are duplicated.
- **Added**: a Bazel regression test on the rlgenerals side (`engine_saves_test`) that spawns a child engine process, loads a save (tracking one scratch-pad map), and asserts that an unrelated file placed in the shared Save directory survives that child's teardown — the pre-fix whole-directory sweep would have deleted it too.

## 03/10/2026
### PLAN-023 Phase 0: a tested init() rethrow site, a real MiniAudio run, and save-path hardening
- **`GameEngine::init`'s rethrow site** (both games): a `GENERALSX_TEST_FAULT_IN_INIT` environment hook, gated on `IsEngineEmbeddedMode()` (a no-op outside embedded mode, so retail and stock builds are unaffected), raises a fault at the top of `init()`'s own try block so a host's test can exercise that function's `catch (const FatalEngineError&) { throw; }` rethrow site specifically, not only a throw site reached before any engine code's own try block is entered. rlgenerals' `test_fault_inside_game_engine_init_raises_engine_fault` (`fault_test.py`) now asserts the raised `EngineFault`'s message is the hook's own text, not just its type: checking the type alone cannot tell this rethrow site apart from the generic `catch (...)` below it, which reaches an `EngineFault` of the same type through its own `RELEASE_CRASH` if the rethrow site were ever removed. `GameState::loadGame`'s own rethrow site gained the same coverage later this session (see the `GENERALSX_TEST_FAULT_IN_LOADGAME` bullet below); the remaining roughly twenty engine-side rethrow sites between `RELEASE_CRASH` and a host entry point are still untested.
- **MiniAudio backend actually run, not just compiled**: the `linux64-miniaudio` CMake preset's `GeneralsMD/GeneralsXZH` binary was linked and run on Linux (Zero Hour assets, Xorg + `llvmpipe`/the host GPU for the Vulkan swapchain). With `-noaudio`, `SDL3GameEngine::createAudioManager` constructs `MiniAudioManagerDummy`; the process booted to the main menu and shut down cleanly. Without it, the same binary constructs the real `MiniAudioManager`, opens an actual playback device through its staged `openDevice`, boots to the main menu and shuts down cleanly. Both runs reach `~MiniAudioManager`, which calls `closeDevice()` directly; since that call runs while the object's dynamic type is `MiniAudioManager` (the derived dummy part has already been destroyed), it is the base class's own staged teardown that runs even for the dummy object, not the dummy's no-op override. These two runs only cover the two ends of `openDevice`'s stage sequence (every stage succeeding, and no stage running at all); the four partial-open `closeDevice` paths -- `openDevice` failing after the resource manager, the log, the context, or at engine init -- were not exercised and have no fault injection yet. PLAN-023's Phase 0 acceptance table is updated accordingly, including that remaining gap.
- **Save-path hardening** (`GameState.cpp`/`GameStateMap.cpp`, both games): non-Windows `iterateSaveFiles`' directory loop advanced with `dirIter.increment(ec)` as a `for` loop's own step, then checked `ec` in the body; both libstdc++ and libc++ reset the iterator to `end` on an `increment` failure, so the loop's own condition went false before that check ever ran, and a mid-read directory error stayed silent. Restructured as a `while` loop that checks `ec` right after each `increment`, before testing against `end`. `extractAndSaveMap` (`GameStateMap.cpp`) now closes its output file (and frees its read buffer) on every throw path, not only the ones it threw itself: on a truncated save, both the size read and the body read end up throwing `XFER_READ_ERROR` out of `XferLoad::xferImplementation` (`beginBlock` itself never throws -- on a short read it `DEBUG_CRASH`es and returns 0 -- but the following `xferUser(buffer, 0)` reaches `xferImplementation`'s `fread(data, 0, 1, fp)`, which returns 0 rather than the 1 it checks for, so it throws there instead). The allocation's null check never fires either way, since `new` throws rather than returning null: with a size of 0 it returns a valid pointer, while a corrupt (as opposed to merely truncated) save can hand `beginBlock` a bogus size that makes the allocation itself throw `ERROR_OUT_OF_MEMORY` instead. Any of these used to leave the file handle open, which failed a later `DeleteFile` of that now-tracked partial file on Windows and leaked one descriptor per failed load elsewhere. `embedInUseMap` (`GameStateMap.cpp`, both games) had the identical defect on the save side: its allocation and `fread` failures freed the read buffer but never closed `fp`, and a write-side failure — `XferSave`'s `XFER_WRITE_ERROR`, thrown from `xferImplementation` (`xferUser`) or `endBlock`, for example on a full disk — left both `fp` and the buffer leaked, since nothing downstream of the `beginBlock`/`xferUser`/`endBlock` sequence was wrapped in a `try`/`catch` at all. Given the same `try`/`catch (...)` treatment as `extractAndSaveMap`: close `fp` and free the buffer before rethrowing, on every one of those paths. Documented, next to `m_scratchPadMaps`, the gap that per-instance tracking does not close: a scratch map left by a process killed before its destructor ran, or by an embedded engine that faulted and was deliberately never destroyed, is cleaned up by nobody. `clearScratchPadMaps` (both games) also used to clear `m_scratchPadMaps` unconditionally after its delete loop, even for a path whose `DeleteFile` failed; before per-instance tracking, the old whole-directory sweep ran again on every `loadGame` and in `~GameStateMap`, so a map that failed to delete once (a transient sharing violation on Windows, or `EBUSY`/`EPERM` on Linux) was retried on the next sweep, and clearing the vector regardless of `DeleteFile`'s result dropped that retry. Now a path is only dropped from `m_scratchPadMaps` once its delete succeeds or the exact tracked path is confirmed gone (not `TheLocalFileSystem->doesFileExist`, which falls back to a case-insensitive directory scan and could keep retrying, and reporting, a path that no longer exists under its tracked name); a path that is still there after a failed delete stays in the vector so the next `clearScratchPadMaps` call or `~GameStateMap` retries it. That "confirmed gone" check itself needed narrowing: `GetFileAttributes` (`stat()` on non-Windows, via `file_compat.h`) returns `INVALID_FILE_ATTRIBUTES` for *any* failure, not only "no such file" -- `EACCES` on a directory that lost its search bit, or `ESTALE`/`EIO` on a network-mounted user-data root, fail `DeleteFile` and the existence check together while the file is still on disk, which silently dropped it from `m_scratchPadMaps` with nothing printed. A new `scratchPadMapIsDefinitelyGone` helper now answers only a definite not-found (`ENOENT`/`ENOTDIR`, or `ERROR_FILE_NOT_FOUND`/`ERROR_PATH_NOT_FOUND` on Windows) and treats every other check failure the same as the path still being there, so it is reported and retried instead of lost track of.
- **`ReleaseCrashLocalized` minidump ordering** (`Core/.../Debug.cpp`): the embedded-mode skip introduced on 02/10 moved `TriggerMiniDump()` to after the two `TheGameText->fetch()` calls and the `AsciiString::translate()` that builds the crash reason, even with the embedded-mode flag off. Moved it back to before the fetches (matching `ReleaseCrash` and the pre-02/10 behaviour): those calls can themselves fault on the corrupt state a crash dump exists to capture, and the minidump should reflect that state, not whatever two more lookups and a translation left behind. Only the `MessageBox`/`ShowWindow`/stderr block, which needs the fetched text, still runs after the fetches.
- **`GameState::loadGame`'s rethrow site** (both games): a `GENERALSX_TEST_FAULT_IN_LOADGAME` environment hook, gated on `IsEngineEmbeddedMode()` the same way `GENERALSX_TEST_FAULT_IN_INIT` is, raises a fault at the top of `loadGame`'s own try block, before `xferSaveData` runs, so a host's test can exercise that function's `catch (const FatalEngineError&) { throw; }` rethrow site through a real save/load round trip rather than a hook called from outside engine code. rlgenerals' `test_fault_inside_game_state_loadgame_raises_engine_fault` (`fault_test.py`) exercises it.
- **`clearScratchPadMaps`'s inline comment** (`GameStateMap.cpp`, both games): the delete loop's own inline comment, right above the `scratchPadMapIsDefinitelyGone` call, was left stale by the Save-path hardening fix above -- it still said the loop would "only report and retry one that is genuinely still there", even though a path whose existence could not be checked at all (an `EACCES`/`ESTALE`/`EIO` stat failure, not a definite not-found) is reported and retried too, which the block comment ten lines above it already said correctly. Reworded to match. rlgenerals' `test_clear_scratch_pad_maps_reports_a_map_whose_existence_cannot_be_checked` (`saves_test.py`) now covers the behaviour itself: denying a child's Save directory its own search (execute) permission, not just its write permission, makes both `DeleteFile` and the `stat()` existence check fail with `EACCES` on the one tracked path, and the fix must still report and keep it instead of treating the check failure as "gone".
- **`GameState::friend_iterateSaveFiles`** (`GameState.h`, both games): a test-only public wrapper over the private `iterateSaveFiles`, for the same reason as `friend_xferSaveDataForCRC`. rlgenerals' `test_iterate_save_files_filters_non_regular_and_is_case_sensitive` (`saves_test.py`) uses it to check the non-Windows scan: case-variant `.sav` files are both listed, and a FIFO, a dangling symlink and a non-`.sav` file are skipped. The open-error and mid-read error-reporting paths are still untested.
